# Combat ECS migration

## Runtime ownership

- `CombatUnit` and its `CombatAttribute` buffer own each chess unit's camp, alive state, position, current attack target, normal skill rotation indices, and all eight combat attributes. `CombatFrameScheduler` advances ECS cooldown and Buff timers, then visits units in friendly-then-enemy, UID order, followed by projectiles and position points in their ECS creation order. Preparation uses the same unit roster order. `EntityQizi` and `CharacterAttribute` are compatibility views for existing UI and skill code.
- A unit's trigger registrations are stored in `CombatTriggerListener` on that same entity. Skills, Buffs, projectiles, and position points also have ordered ECS trigger-group buffers. Activation, destruction, and event dispatch select trigger slots through these buffers; managed maps only resolve the current `OneTrigger` object.
- Trigger-group recompilation compares authored trigger types with the ECS buffer directly. `TriggerList` no longer keeps a second managed type array; a stale group handle after World recreation is rebuilt on the next dispatch.
- Cooldown and buff timer values live in ECS components. The skill component also computes cooldown reduction and owns each cast's duration, shake and animation timings, and trigger value. The buff component owns its active and valid flags, shield value, owner, ID, tags, duration, aura queue order, and current-tick reset state. Buff stack checks, ID removal, shield selection, aura promotion, per-frame buff iteration, and death-time timer pausing query these ECS components. `CurBuffList` remains a compatibility view for UI and managed object cleanup. Managed `Skill` and `Buff` objects still resolve synchronous callbacks.
- Skill destruction resets the remaining cooldown and default cast timings in one `CombatCooldown` update after its synchronous destruction callbacks.
- The battle board owns the Buff tick and activation/aura order counters, along with the pending cooldown and Buff step durations consumed by their ECS systems.
- Each `OneTrigger` condition tree is compiled into an ECS `CombatConditionNode` buffer. Timed nodes keep their accumulated time and pass count in that buffer and advance only when evaluated. Group short-circuiting and chance draws remain synchronous and ordered.
- `OneTrigger` checks its condition, command, and picker program entities before each use. A cached handle from a previous ECS World is recompiled from authoring data after World recreation; command callback indices are rebuilt with the command program.
- Condition evaluation re-reads its ECS node buffer after synchronous callbacks. A callback can change the entity structure without leaving an outer condition group using a stale `DynamicBuffer` view; group child order and timed-node writes remain immediate.
- Each `OneTrigger` invocation writes selected target identities into its own ECS `CombatSelectedTarget` buffer as pickers find them. Recursive invocations have separate buffers and temporary ordered callback projections. Every serialized command type is compiled into an ECS `CombatCommandNode` buffer; unknown command types fail compilation rather than falling back to `CommandBase.OnExecute`. Repeat nodes execute their children synchronously. Attribute, damage, Buff removal, projectile removal, and Buff/projectile/position-point creation nodes read the ECS target snapshot; attribute changes and shield creation/removal write directly to ECS combat attributes and buff values. Damage nodes calculate each target's damage from current ECS attributes immediately before its synchronous callback. Creation, removal, and presentation nodes invoke ordered managed callbacks for authoring-data cloning, Unity objects, and destruction.
- The authored target-picker tree, including nested random pickers, is compiled into an ECS `CombatTargetPickerNode` buffer. The AOT program bridge dispatches every picker kind and executes camp, range, angle, bullet, damage-source, and random-count rules from those nodes. The picker classes retain authoring serialization but no longer have parallel `GetTarget` runtime methods. Hot-update callbacks supply source inputs, item-table queries, and ordered object projection.
- The AOT trigger invocation bridge now evaluates the condition, creates/releases that invocation's ECS target buffer, and invokes target picking before commands. The hot-update object still supplies authored picker inputs and synchronous object/presentation callbacks.
- Target pickers now receive their invocation's ECS selection handle as an explicit argument, including nested random pickers. `OneTrigger` no longer stores a mutable active-selection handle across recursive trigger calls.
- `OneTrigger` no longer owns `CurTargetList`. Each invocation keeps a temporary managed projection of the ECS target buffer solely for synchronous object callbacks; recursive invocations cannot replace an outer call's projection.
- Command execution copies its ECS command nodes and selected target identities into temporary native arrays for the duration of one invocation. The snapshots preserve command and target order if synchronous callbacks change or release their ECS entities, without allocating managed arrays per invocation.
- The hot-update command callback projection borrows a pooled list for the same invocation instead of allocating a command-object array on every trigger.
- Command object and presentation callbacks now implement one interface in `CombatCommandCallbacks`. `OneTrigger` only starts the ECS command program; the adapter keeps a pooled command snapshot so recursive callbacks cannot replace the outer invocation's command objects.
- Damage-trigger gating and temporary-versus-table Buff creation are compiled into command nodes. The hot-update damage and Buff callbacks use those node values, retaining managed objects only for synchronous triggers, cloning, and table access.
- Recursive invocation depth now lives on the ECS condition-program entity. Releasing a condition program during its own callback defers entity destruction until its outermost invocation exits.
- Repeat count rules and parameters are compiled into ECS command nodes. The AOT executor chooses fixed or parent-item count at the original execution point; item-dependent counts use only an item-table lookup callback.
- Template Buff creation compiles its ordered Buff IDs into a `CombatCommandBuffId` ECS buffer. The command runner visits each selected target and then each compiled Buff ID; the hot-update callback only constructs the corresponding Buff object and runs its existing activation path.
- Projectile creation compiles its projectile ID, integer parameter, and spawn offset into the ECS command node. The hot-update callback creates the projectile and applies its trigger/GameObject presentation; bullet initialization takes the compiled integer directly instead of a temporary managed parameter list.
- Position-point creation compiles its placement mode, duration, facing option, and offset bounds into the ECS command node. `CombatSpawnPlacement` resolves both projectile and point spawn positions from those nodes, drawing random offsets from the existing logic RNG in the same order. The hot-update callbacks still create visible objects and fire their triggers.
- Animation, audio, SFX, and weapon commands compile their presentation subtype and fixed configuration into ECS command nodes. The callbacks apply those nodes to Unity objects; skill-dependent weapon item IDs and live animation timing remain resolved at execution time.
- Random target count rules are evaluated in the ECS selector. Item-dependent counts still use a synchronous item-table callback; the logic RNG is called only after a positive count is resolved.
- When a random target count resolves to zero, the selector clears its ECS candidates and selected targets, and the hot-update projection is cleared before commands run.
- Shield Buff consumption and shield/HP attribute writes run through ECS data with synchronous managed callbacks when a Buff is depleted. Before/after damage triggers, death presentation, and damage numbers remain in the hot-update layer.
- Death handling pauses active Buff timers, clears the unit's current board occupancy, and checks the surviving update group in ECS, preserving the original pause-before-presentation order. The hot-update layer sends the existing battle-stop event when ECS reports the result.
- Normal skill rotation, power eligibility, old-target range checks, cast index advancement, and power spending read or update ECS unit data. The active normal attack's elapsed time and one-shot shake/animation flags live in `CombatAttackCast` on the unit. The FSM invokes animation and skill callbacks in their original order.
- A unit's ordered normal, automatic, passive, and special skill definitions live in its `CombatSkillSlot` buffer. Normal cast costs, ranges, and target types read this buffer. ECS checks each automatic slot's live cooldown immediately before its synchronous hot-update cast callback, so an earlier cast can still affect later slots in the same tick. Passive skills also activate in buffer order.
- Nearest, radius, and sector targeting read `CombatUnit` components. Group roster queries for area bullets and position-point placement also read `CombatUnit`, then resolve UID values to managed callback targets in the original order. Bullet picking filters `CombatProjectile` by ID, caster UID, and alive state; creation-time pending bullets use the same filter in the hot-update layer. Random list selection shuffles candidate indices and stores both chosen indices and identities in the invocation's ECS buffers while drawing from the existing logic RNG. Object pickers still resolve their managed targets in the hot-update layer.
- Normal attacks and nearest-target pickers call the ECS nearest query directly; the hot-update layer only resolves the returned UID when it needs the current object for a synchronous callback.
- Nearest, distance, and sector trigger pickers now let `CombatSpatialSelection` write unit handles directly into the invocation's ECS target buffer. The hot-update callback projects each UID to the matching `EntityQizi` in the same order.
- Spatial picker range rules now resolve through the AOT selection bridge. The sector picker reads its facing target, source camp, and both positions from ECS unit data; hot-update callbacks only check that the facing target has a managed object, query an item's authored weapon length when needed, and project selected units.
- Current-attack-target and damage-related-target pickers resolve their unit identity through `CombatIdentitySelection`. Null targets retain an explicit `None` slot in both the ECS buffer and hot-update projection.
- Projectile target picking merges ECS-registered projectiles with the hot-update layer's creation-time pending candidates in one AOT selection pass. The AOT pass sorts by spawn order and writes each projectile's current handle, including a pending projectile that has already created its ECS entity but has not registered its identity yet.
- Projectile and position-point spawn-order counters live on the ECS battle board and reset at their existing cleanup points.
- All four bullet types keep position, camp, and alive state in `CombatProjectile`. Tracking bullets also keep speed and target entity there. Mark-point bullets keep lifetime progress there. Rotating bullets keep orbit state in `CombatOrbitProjectile`. Penetrating bullets keep their Bezier curve, traveled distance, and hit UID buffer in ECS. Bullet ticking, target picking, and cleanup query projectile entities and preserve creation order. A short-lived pending list keeps bullets visible to synchronous callbacks before their projectile entity is registered. Managed bullet objects still draw random control-point inputs, invoke ordered tick and hit triggers, and update GameObjects after the ECS step.
- Penetrating and orbit bullet hit passes now visit the ECS opposing-unit roster in UID order and resolve managed objects only for synchronous hit callbacks.
- Penetrating and orbit bullets borrow an ordered UID list for each hit pass instead of allocating a captured visitor delegate per projectile tick. Profiler markers now split projectile ticks by bullet type, mark-point ticks into trigger, timer, and SFX work, and trigger invocations into picker and command work.
- Penetrating bullet hit checks use the current projectile position for a cheap squared-distance rejection before fetching the projectile entity and its hit history. A synchronous hit callback refreshes that position before scanning later targets, preserving callback-driven projectile movement.
- The projectile phase builds a one-step unit spatial index with a Burst `IJobParallelFor`. Penetrating bullets query nearby ECS unit positions and run hit callbacks in UID order. A unit mutation after the index is built, or a hit callback that changes the bullet's position, switches the remaining checks to the live ordered roster so synchronous trigger effects remain visible in the same step.
- When at least 32 non-tracking Bezier projectiles exist, a Burst job calculates their next positions and tangents from one ECS snapshot while the main thread builds the unit spatial index and projectile roster. Each bullet still runs its per-tick trigger and hit callbacks in spawn order. If its speed, position, or curve changed since the snapshot, it uses the original immediate Bezier step. Tracking Bezier projectiles always use that immediate path.
- Mark-point bullet Buffs use `CombatBuffTimer` with a projectile owner handle. Their tick, ID removal, and bullet-death cleanup enumerate ECS active timers; `BuffList` remains a managed cleanup view while Buff trigger callbacks stay synchronous.
- Unit and mark-point Buff expiry is decided from `CombatBuffTimer` immediately after its current-tick adjustment. The hot-update layer invokes the resulting destruction or per-tick trigger in the original roster order.
- Incoming Buff layer limits, aura queueing, duration refresh, and replacement selection are decided from `CombatBuffTimer` data. Destruction and activation still call the existing hot-update triggers synchronously.
- Buff destruction now atomically clears valid and enabled state in `CombatBuffTimer`. Aura classification and tag checks read the timer after its identity is bound; before binding they use authored values because table Buffs can set duration before their tags and layer limit.
- Inactive aura Buffs waiting for end-of-tick object cleanup are queued as timer handles in a buffer on their owner unit. The hot-update layer resolves those handles only when releasing pooled Buff objects.
- Position points keep position, camp, validity, and lifetime in `CombatPosPoint`. The point tick scheduler queries ECS entities in creation order; managed point objects still invoke synchronous triggers and manage SFX GameObjects.
- Crowded position-point placement reads the ECS unit roster and positions, then runs the original angle sweep in the AOT combat layer. The hot-update command still creates the point object and fires its triggers.
- The 8×7 board's occupant UID values and pathfinding cell coordinates live in a `CombatBoardCell` ECS buffer. Placement, swapping, movement, death, and path search use that buffer. The hot-update layer supplies the grid's authored cell positions and presents the resulting movement.
- The battle/preparation phase lives on the `CombatBoard` ECS entity. The hero manager, unit idle behavior, and drag UI read the same phase value; battle start and cleanup write it at their existing transition points. Idle units also check their ECS board occupancy before starting combat behavior.
- The battle state's fixed-step accumulator lives on `CombatBoard`; the procedure adds frame time and consumes one ECS step before each synchronous hot-update callback.
- Battle frames retain at most three 60 Hz logic steps in the accumulator. Under overload, older unprocessed time is discarded so a slow frame cannot trigger an escalating catch-up loop. Damage-number and HP-bar presentation run once per rendered battle frame; `Combat.*` Profiler markers separate timer, unit, projectile, point, and unit-skill costs without Deep Profile.
- Unit roster scans reuse their ECS query within one World. They still read and sort the current group before each group's callbacks so units spawned during the first group can enter the second group in the same logic step.
- The battle start timestamp and pending win/loss result also live on `CombatBoard`. The procedure consumes the first queued result before checking the time limit and changing states, preserving the original event order.
- Board geometry initialization and trigger-listener registration IDs are tracked by `CombatBoard` instead of process-wide static counters or flags.
- Chess-unit UIDs are allocated from `CombatBoard` and reset there on GameOver; the hero manager no longer keeps a second UID counter.
- Each friendly unit's deployment snapshot lives in `CombatUnit`. Battle start copies its ECS board cell to the snapshot; battle reset restores it across the unit's ECS reconstruction. Save data reads the snapshot from ECS.
- Dragging one deployed unit onto another swaps both occupant UIDs in a single ECS board operation, then synchronizes their presentation positions.
- The ECS board buffer also resolves the first empty cell and mouse hit cells from its stored geometry. The hot-update layer supplies the authored grid positions and the current board transform offset.
- The board's world offset now lives on `CombatBoard`; world cell positions and mouse hit cells read the ECS geometry and offset together. The hero manager still moves the visible grid GameObject.
- Chess-unit row and column mirrors have been removed from `EntityQizi`; formation UI, reset, and movement read the current cell from the ECS board occupancy buffer.
- An active cell move keeps its start, end, and elapsed time in `CombatMovement` on the unit. The FSM asks ECS to advance the step, then updates the GameObject position and chooses the next state or path cell.

## Target architecture

1. Load existing skill and buff files as authoring data, then move the remaining target-selection decisions and command effects into ECS execution alongside the condition, picker, and command programs.
2. Process combat input, trigger events, target selection, effects, buffs, death, and timer updates in an explicit fixed-step order.
3. Emit presentation events for animation, sound, visual effects, damage numbers, and UI. The presentation layer may keep `EntityQizi` and GameObjects but must not own combat state.
4. Remove `OneTrigger.OnTrigger`, the remaining managed buff state, and the compatibility views once all serialized command types have an ECS implementation.

The current code is in migration. The AOT invocation bridge owns condition-to-target-to-command sequencing and the ECS target buffer lifetime. `OneTrigger` still supplies ordered hot-update callbacks. Condition and command trees execute through ECS buffers, with callbacks for random draws, item table queries, and object or presentation effects. `CommandBase.OnExecute` and its parallel command implementations have been removed; managed command methods now only serve the ECS program's required object and presentation callbacks. Picker dispatch runs from ECS nodes; source retrieval and object projection still call into the hot-update assembly. New combat behavior should be implemented in the ECS runtime rather than adding another managed state mirror.

`CommandRepeatExecuteCmd`, damage triggers, and buff activation can recursively execute commands before the outer command returns. The command program keeps that order. A future event pipeline must also preserve it.
